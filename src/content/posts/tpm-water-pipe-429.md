这篇文章经历了两次写作。第一次是 9 月 10 日，我把一次子代理 429 排障的根因定为 TPM 限流，文章写得很自洽。两周后同一个症状复发，这次我拿到了新证据，发现当时的根因判断是错的——429 根本不是限流，是上游伪装的。所以现在你看到的版本是重写过的：既讲清楚当时的排查过程，也讲清楚我当时的推理在哪一步跳了。误诊的复盘比正确的答案更值钱。

## 一、这套链路是怎么搭的

```text
Claude Code（主会话 + 子代理）
   → 自建网关（协议转换）
      ├→ 渠道一：CLIProxyAPI → 单个 antigravity 账号 → gemini-3.8-flash
      └→ 渠道二：智谱官方 API → glm-5.3-flash
```

主会话挂在 gemini 通道上重度使用几个月，读代码库、几十万 token 的长对话，一次限流没触发过。某天想提速，把两个子代理也指到这条通道上并行干活，开出不到一分钟，双双 429：

```text
API Error: Request rejected (429)
All credentials for model gemini-3.8-flash-high are cooling down
```

同一个模型、同一个账号、同一类请求。为什么主会话怎么用都没事，子代理一上岗就死？这就是当时的题面。

## 二、当时查到的三层，和最终定错的那个根因

第一层是配置：子代理模型的环境变量里模型名带了个手误的括号，所有子代理请求 422。修掉，问题没完。这一层是真的。

第二层是放大器：CLIProxyAPI 的单向冷却闩锁（issue #5611）。上游返回一次 429，它就把凭据锁到预测恢复时间点，期间不再试探，额度回了也不放行。表现是"本该慢一点的降级"变成"全断电"，重启进程才清锁。这一层也是真的，但它只是放大器，不是根因。

第三层，当时我定的根因：子代理的请求节奏抽干了 TPM（每分钟 token 限额）。推理过程是——主会话有人类刹车（读输出、思考、打字，一来一回几十秒），子代理全自动十几秒一轮；每轮发成对的两条几乎相同的请求；无状态 API 导致每轮全量重发对话历史加工具清单，单条 60~70KB。粗算每分钟烧十多万 token，而单个 OAuth 账号的 TPM 就在这个量级。"雪球滚了 11 分钟终于滚过水管口径"——这个解释当时让我非常满意，因为它把所有现象都装进去了：为什么主会话没事（节奏慢）、为什么子代理死（节奏快）、为什么两个并发死得更快（翻倍）。

两周后我知道了它错在哪：**这个解释把"能装下所有现象"当成了"被验证"。我全程没有做过一个对照：去测那一刻 TPM 是不是真的超了。** 网关数据库里躺着每条请求的用量，一条按分钟聚合的 SQL 就能验证"死亡时刻流速是否顶到天花板"——我当时没查，因为 TPM 解释太自洽了，自洽到我没觉得它需要验证。

## 三、TPM 机制本身是对的，这部分知识仍然值钱

先说清楚：错的不是 TPM 机制，是归因。机制部分照讲，这部分我后来反复用到。

多数人对限流的直觉是"水池"模型：账号有总额度，用一点少一点，用完才触发风控。但 TPM 是"水管"模型：不管你一天用多少，只管任何一分钟里流过多少。水管对谁都一样粗，区别只在你用什么姿势用水。主会话一杯一杯接（人类是天然的刹车、流式输出几十秒、工具执行期间管道都闲着），子代理是持续高压。这个模型后来帮我做过好几次容量预算：并发数 × 每分钟轮次 × 每轮 token ≈ TPM 需求，超过管道口径，调什么提示词都没用。

还有一个真实的度量收获。gemini 通道死得太快没法量化，我把同样的双代理负载换到智谱通道上跑了一轮，110 秒 15 条请求全部正常，顺手在网关侧按分钟聚合用量：

| 指标 | 数值 |
|---|---|
| 峰值分钟毛吞吐 | 约 26 万 token |
| 其中缓存读 | 26.1 万（82%） |
| 净新增 | 约 5.6 万 |

两个结论现在依然成立：一是按量付费接口和 OAuth 订阅转出来的通道，TPM 口径本来就不是为同一种负载设计的；二是上下文缓存是隐形救星——子代理每轮重发的大包从第二轮起 93% 走缓存读，基本不占限流额度。选通道时带不带缓存，差的不只是钱。网关把每条请求的 usage 落库、出事时一条 SQL 按分钟聚合流速，这个"电表"后来成了我每次排障的第一站。

## 四、两周后的翻案：429 是伪装的

9 月 23 日，升级了 CLIProxyAPI 版本之后，我在同一通道上做过一次判别实验：三个子代理并发，轻负载，零 429。如果是 TPM 天花板，这个负载组合不可能全过——第一次出现与"流速"解释矛盾的数据。

当晚正式任务里子代理再次连环 429，这次我补上了当时缺的那个对照：发一条不带 system prompt 的轻量请求，同一个模型同一个凭据，200，秒回。额度如果真耗尽，轻请求没有豁免权。429 是选择性的，而选择标准不在用量里——在子代理的 system prompt 里：任何 Agent 框架派生子代理时都会注入框架身份声明，这个指纹会触发 Google 的内容过滤，而 Google 的网关在过滤命中时返回的正是 429 RESOURCE_EXHAUSTED，一个伪装成限流的拒绝。CLIProxyAPI 的官方 issue #5695 记录了同样的现象和机制。

为什么主会话没事、子代理必死？不是节奏快慢，是带不带那段身份声明。为什么当时看起来像 TPM？因为闩锁放大器的存在让"冷却时间"和"用量恢复周期"纠缠在一起，非常像流速问题。

这次的完整排查和修复（敏感词混淆、出口 IP 质量、降级保交付）写在续篇《不是额度，是指纹》里，这里不重复。

## 五、修正后的药方，按性价比排序

1. **分流**（当天可做）：主会话和子代理走不同通道，一行配置的事——子代理模型指定到另一条通道，爆炸半径同时隔离。这条当时就做了，现在看依然是对的，只是理由从"抢 TPM"变成了"抢同一个故障域"
2. **接电表**：网关侧把每条请求的 usage 落库。排障第一件事永远是按分钟聚合看流速、看状态码分布，而不是看错误提示脑补机制
3. **遇到限流类错误，先做对照实验**：找一条"如果错误是真的，就不该活着"的请求。轻量请求、无 system 请求、换个通道的同构请求，任何一个活口都能推翻错误码的字面说法
4. **升级代理层版本、补齐配置**：我这次排障里 sensitive-words 配置半截没配，官方修复只吃了一半药，这类"升级了但没升完整"的状态值得专门检查
5. 凭据池降级为可选项：单凭据跑子代理并发在这套修复之后是可用的，并发规模再上一个量级才需要

## 六、误诊复盘：比根因更重要的三条

第一，自洽不等于被验证。TPM 解释能装下所有现象，我当时就把它当结论发了。装下所有现象只是候选资格，验证的方式是去找"如果它是真的，就应该出现/不该出现"的数据——那条一分钟就能跑的聚合 SQL，我两周后才补跑。

第二，错误码是线索不是证据。429 可以是限流，可以是内容过滤的伪装，还可以是别的。排障时把错误码当"上游亲口告诉你的事实"，就会像我一样在错误的方向上把故事讲圆。

第三，排障结论要有"可推翻性"。现在每定一个根因，我都强迫自己写一行："什么现象出现，就说明这个结论错了。"TPM 结论的可推翻条件应该是"同等流速下有请求活着"——9 月 23 日晚轻请求 200 的那一刻，这个条件就成立了。

标题我留着没改。TPM 是水管不是水池，这个模型本身是对的，它教我理解了限流；错的是我把一段水管的故事，安在了一场火灾头上。
