# TPM 是水管，不是水池：为什么主对话永不 429，子代理一开就阵亡

## 现象：同一个账号，一边永远健康，一边秒阵亡

先把链路交代清楚，这是一套很典型的个人 AI 基建：

```
Claude Code（主会话 + 子代理）
   → AxonHub（协议转换网关）
      ├→ 渠道一：CLIProxyAPI → 单个 antigravity 账号 → gemini-3.8-flash
      └→ 渠道二：智谱官方 API → glm-5.3-flash
```

主会话挂在 gemini-3.8-flash 上天天重度使用，跑了几个月，**一次限流都没触发过**。大到读整个代码库、长对话滚到几十万 token，都没事。

直到某天想提速，把子代理也指到 gemini-3.8-flash 上并行干活。结果：**开出不到一分钟，两个子代理双双阵亡**，错误原文长这样：

```
API Error: Request rejected (429)
All credentials for model gemini-3.8-flash-high are cooling down via provider antigravity
```

同一个模型、同一个账号、同一类请求。为什么主会话怎么用都没事，子代理一上岗就死？

## 排障：剥了三层洋葱

第一层是配置问题：`CLAUDE_CODE_SUBAGENT_MODEL` 环境变量里模型名带了个手误的括号，导致所有子代理 422。修掉，问题没完。

第二层是 CLIProxyAPI 的**单向冷却闩锁**（GitHub issue #5611，官方已关）：上游只要返回一次 429，它就把账号锁到"预测恢复时间点"，期间**永远不再试探**——哪怕额度已经回充了也不放行。表现就是：本来该"慢一点"的降级，变成了"全断电"，重启进程才能清锁。这是放大器，但不是根因。

第三层才是真根因，也是这篇博客想讲清楚的事：

**不是用量超了，是每分钟的流速超了。子代理的请求节奏，天然就是抽干 TPM 的形态。**

## 机理：TPM 是水管，不是水池

很多人（包括排障之前的我）对限流的直觉是"水池"模型：账号有额度，用一点少一点，用完才触发风控。所以"我主会话天天用都没事，加两个代理怎么就爆了"——因为实际上 TPM（Tokens Per Minute，每分钟令牌数）是**水管**模型：它不管你一天用多少，只管**任何一分钟里流过多少**。水管对谁都一样粗，区别只在你用什么姿势用水。

主会话的用水姿势是"一杯一杯接"，它有三个天然限速器：

1. **人就是刹车**。我要读输出、要思考、要打字，一来一回几十秒到几分钟，水管闲着
2. **流式输出很慢**。长回答光吐字就要几十秒，这期间水管也是闲着的
3. **工具执行要时间**。查日志、等监控、跑测试，水管还是闲着的

子代理的用水姿势是"消防栓全开"：

1. 中间没有人类，上一轮一结束下一轮立刻发，十几秒一轮全自动连发
2. 每轮还不是一个请求，是**几乎一样的两条**（Claude Code 的双流机制，差几百字节的成对请求），双倍烧
3. 最狠的一点：LLM 接口是无状态的，**每条请求都要把"完整对话历史 + 系统提示 + 工具清单"整个重发一遍**，单条 60~70KB，约 1.8 万 token。于是包袱越滚越大，越到后面每轮烧得越多——第一个子代理好好跑了 11 分钟才死，就是雪球滚了 11 分钟终于滚过了水管口径

粗算一笔账：

| 消费者 | 节奏 | 每分钟烧多少 |
|---|---|---|
| 主会话 | 人读人想人打字 | 断断续续，从未顶到上限 |
| 子代理 ×1 | 十几秒一轮 × 成对两条 | 10~18 万 token |
| 子代理 ×2 并发 | 机器速度 × 2 | 直接翻倍，秒穿天花板 |

而单个 antigravity 账号的水管口径，恰好就在十几万这个量级。

还有个隐蔽的爆炸半径：**同一个账号上的所有消费者共享一根水管**。子代理把池子抽干的瞬间，挂在同一账号上的主会话也跟着 429——主会话不是免疫风控，只是它自己的节奏从来没碰到过线；一旦有人替它把线碰了，它一样挨打。我排障当天就亲历了一次：子代理风暴一起，我的主会话同步开始报 429。

## 对照实验：换条管道，顺便拿到硬数字

gemini 这条管道死得太快，没法量化。我把同样的双代理负载换到智谱 glm-5.3-flash 上跑：110 秒，15 条请求全部正常返回，零限流。顺手在 AxonHub 侧把每次请求的用量按分钟聚合（网关把每条请求的 usage 落进 PostgreSQL 的 requests 表，一条 SQL 的事），拿到了一组很有说服力的数字：

| 指标 | 数值 |
|---|---|
| 峰值分钟毛吞吐 | 约 26 万 token |
| 全程毛吞吐 | 31.7 万 token |
| 其中缓存读 | 26.1 万（82%） |
| 净新增 token | 仅约 5.6 万 |

这组数字说了两件事：

**第一，天花板差了一个量级。** 同样的烧法，单账号会员通道十几万就烧穿，智谱干到 26 万/分钟面不改色。会员 OAuth 转出来的 API 和正经按量付费接口的 TPM 口径，本来就不是为同一种负载设计的。

**第二，上下文缓存是隐形的救星。** 子代理每轮重发的那 1.8 万 token 大包，从第二轮起 93% 被智谱识别为"跟上轮一样"，走了缓存读——又便宜、基本不占限流额度。所以"净新增"每分钟只有 2 万左右。同样一脚油门，有缓存的管道表走得慢得多。

顺带一提那个"电表"：网关把每条请求的 usage 落进数据库，出事时一条 SQL 按分钟聚合，流速、命中率、天花板全都能算出来。**你无法管理你没有度量的东西**——这次排障真正的转折点，不是改配置，是把电表接上了。

## 修复方案，按性价比排序

1. **分流（当天可做）**：主会话和子代理走不同的渠道。主会话节奏慢，配得上窄但便宜的水管；子代理是吞吐怪兽，扔到口径大、带缓存的管道上。在 Claude Code 里就是 `CLAUDE_CODE_SUBAGENT_MODEL` 一行配置的事。附赠一个好处——爆炸半径隔离，一边死了不殃及另一边
2. **凭据池（根治）**：如果非要用单账号通道跑并发，唯一解是多搞几个账号做轮换池，把流量摊到多根水管上。任何参数调优都绕不开物理口径
3. **选带上下文缓存的供应商**：无状态 API 的"每轮全量重发"是逃不掉的税，但缓存能把这笔税从"烧额度"变成"读缓存"
4. **网关侧主动节流（可选）**：在 AxonHub 上按渠道配 TPM 预算，超额先垫队再转发，别把上游打炸

## 三条可以带走的话

- **开并发之前先算预算**：并发数 × 每分钟轮次 × 每轮 token ≈ 你的 TPM 需求。这个数超过管道口径，怎么调提示词都没用
- **限流从来是共享资源的引爆点**：同账号、同渠道、同凭据的消费者互相伤害，接电表的时候要按"渠道"维度聚合，不要按"消费者"维度
- **当心降级放大器**：闩锁型的冷却实现会把"慢一点"变成"全断电"。如果你的代理层有限流重试逻辑，值得专门测一次"触发之后能不能自己恢复"

最后一点感想。给 AI Agent 加并发是最廉价的提速诱惑——多开一个进程不要钱。但水管口径是别人定的规则，你的消费模型从"一天用多少"瞬间变成了"这一分钟流多少"。这是所有想把 LLM 当基础设施来用的人，迟早要交的一次学费。我交过了，电表现在常亮。
