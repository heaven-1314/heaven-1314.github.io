三周前我写过一篇《TPM 是水管，不是水池》，把子代理的连环 429 归因为限流机制，还挺自洽。这次的故事证明：那个结论只对了一半——**429 这个错误码本身，就可以是说谎的**。

## 起因：子代理连环阵亡

走 CPA（CLIProxyAPI）反代 Antigravity 订阅用谷歌模型，是我跑了很久的通道：主对话重度使用从没出过事。深夜我照常开了个子代理跑长任务，几分钟后它死于：

```text
429 · All credentials for model xxx are cooling down
(last error: RESOURCE_EXHAUSTED 之类上游原文)
```

字面翻译：额度耗尽，所有凭据冷却中。而当天早些时候我还做过判别实验——三个子代理并发，零 429。中间隔着的只有几小时的轻度使用。**额度像一夜之间蒸发又不像**，这个别扭感是整个排障的起点。

## 第一层：429 说谎了

两个证据把“额度耗尽”推翻：

**证据一，冷却截止后的对照组。** 网关快照显示冷却计时在 21：17：09 截止。截止之后子代理的请求继续 429，而我手工发的一条不带 system prompt 的轻量请求——同一个模型、同一个凭据池——200，秒回。额度如果真没了，轻请求没有豁免权。

**证据二，上游官方 issue。** CLIProxyAPI 的 issue #5695 描述了一模一样的现象：主 agent 正常、子代理必 429、**额度明明可用**。维护者的结论：90%+ 的这类案例，是子代理请求里注入的专属 system prompt（身份声明如"Claude Agent SDK"字样）触发了上游的内容过滤，而 Google 的网关在过滤命中时，**用 429 RESOURCE_EXHAUSTED 作为伪装响应**。不是额度问题，是指纹问题。换句话说，罪魁不是某个具体框架——任何 Agent 框架派生子代理时都会注入自己的身份声明，走这条路就都可能踩中同一个过滤器。

修复方式是官方给的两味药：升级 + 把触发词加进配置的 `sensitive-words` 列表，让网关在发往上游前用零宽字符把这些短语混淆掉。我们此前只吃了第一味（升级了二进制），第二味（配置层）一直没配——所以“白天实验通过、晚上正式任务暴毙”完全说得通：实验的子代理没踩词，正式任务的提示词踩了。

补上配置，重启，429 消失。但下一层立刻露头。

## 第二层：400 接班

重启后错误变成了：

```text
400 · User location is not supported for the API use
```

意思变成了：你的出口 IP 地区不受支持。排查过程抓到两个真相：

**真相一，重启打散了钉在干净出口上的连接。** 网关到上游走代理，keepalive 长连接长期钉在一个干净的出口节点上。重启把连接池清空，新连接按代理组的当前指向走——落到了香港，一个 Google API 不支持的地区。**“重启前是好的”和“重启后坏了”可以同时为真**，因为它们走的根本不是同一条路。

**真相二，分流比想象的复杂。** 抓现行连接发现，这个服务对上游的请求分散在**两个域名**上，分别命中**两个不同的代理组**：一个组一个月前排障时锁定过干净节点，另一个组一直开着自动选择、悄悄落到香港——**只锁一个组等于只修了一半的路**。

修法很朴素也很费机器：**金标准逐节点轮测**。每个候选节点执行一遍“切组 → 重启网关 → 发真实调用 → 看状态码”，一轮十几秒。十七个节点测完，**只有一个是干净的**——流媒体优化 IP、广播段 IP、打着“原生”标签的 IP，全部被上游标记拒绝。

中间还踩了个数据陷阱：轮测脚本里切组 API 报错被重定向吞掉了，组根本没切走，探针打在旧节点上照样 200——两个“可用节点”的数据全是假阳性。修正脚本、校验每次切组的返回码之后，独苗还是独苗，假阳性归零。教训配得上加粗：**面板上测通的节点不等于 API 放行的节点，金标准只有真实调用。**

## 第三层：玄学的间歇拒绝

两层修完，轻量请求十连发全部 200。开子代理——跑了三轮，死。错误还是 400，但这次是**间歇性**的：几百字节的小请求稳定通过，一百多 KB、带完整工具链的流式大请求，大约一半概率被拒。

小请求和大请求的区别不在额度、不在地区，而在上游 WAF 的深度检查阈值。对长任务这是死刑：几十轮请求、每轮五成死亡率，全程存活的概率约等于零。当晚的处置是务实的——**换稳定通道保交付，排障不阻塞交付**——长任务在另一个模型通道上顺利完成。

戏剧性的是次日：同一个节点、同样的子代理、同样的任务形态，52 次工具调用，**零失败**跑完全程。间歇拒绝没有复发。定性：上游边缘的暂时性抽风，观测而非修复。

## 方法论沉淀

这次排障沉淀了五条纪律，比修复本身更值钱：

1. **错误码会说谎。** 429 可以是内容过滤的伪装，400 可以是地区封锁也可以是深度检查，错误文本不是事实陈述，是线索。
2. **金标准只有真实调用。** 面板测延迟、测连通、测解锁都不算数，全链路真实请求的返回码才算数。
3. **证据要三源对账。** 网关的请求流水、错误日志的原始报文、agent 侧的运行记录——单看任何一处都可能被表象骗，三处对不上就是翻案的起点。
4. **修好一层别宣布胜利。** 每一层的修复都会改变系统的行为面，把下一层顶到前台。三层病只有全部走完才知道全貌。
5. **交付与排障解耦。** 生产任务永远留一条稳定降级通道，排障可以慢慢做，deadline 不能陪葬。

三周前那篇“水管论”教我看限流的机制，这次教我看错误码的修辞。下次再见到 RESOURCE_EXHAUSTED，我第一个问题不会是“额度还剩多少”，而是“**这条错误消息，是谁想让我看到的**”。
